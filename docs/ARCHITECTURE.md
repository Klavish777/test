# Архитектура Work Day

## Слои

```
ui/            Compose-экраны + один WorkDayViewModel. Никакой бизнес-логики: только команды и отображение.
domain/engine/ ShiftEngine — единственное место, где «течёт» смена: фазы, тики, очереди, отчёты.
domain/agent/  GrowthAgent (контракт) + 4 персоны. Планирование — чистая функция, генерация — suspend.
domain/model/  Доменные типы и словарь 24 действий (TaskKind). Не знают ни про Compose, ни про сеть.
data/          LlmClient (remote/offline), репозитории, YouTube Data API, импорт CSV.
core/          PersistedStore — персист на одном JSON-файле.
di/            AppContainer: ручной граф объектов, живёт в Application.
```

Поток в одну сторону: `ui → engine → agent → data`, обратно — только через `StateFlow`.
Экраны читают `ShiftEngine.state` и `WorkspaceRepository.state`, сами ничего не считают,
кроме форматирования.

## Модель смены

Сутки жизни канала сжимаются в «рабочий день» 09:00–18:00. Тик = 250 мс реального времени = 6 минут смены
(делится на множитель скорости 1×–8×). На каждом тике каждый включённый агент либо ведёт свою текущую
задачу (прогресс += 6/effortMin × интенсивность), либо берёт из плана первую задачу, чей слот наступил.

Фазы: `IDLE → PLANNING → WORKING → REPORTING → FINISHED`, плюс `PAUSED` (останавливает цикл, состояние сохраняется).

Что делает смену приложением, а не демо:
* план строится из **включённых плейбуков** и **интенсивности**, а не из жёсткого списка;
* у каждой задачи есть риск (`LOW/MEDIUM/HIGH`) — он решает, закроется задача сама или встанет на одобрение;
* материалы складываются в `artifacts` и переживают перезапуск (лежат в `workspace.json`);
* вечерний отчёт считает оценку агента как сумму `impact` закрытых задач, а не «число кликов».

## Почему ручной DI и JSON вместо Room/Hilt

Минимальный набор зависимостей важнее красивого графа: в проекте нет ни kapt, ни ksp, ни Room-миграций.
`PersistedStore<T>` делает атомарную запись (`.tmp` + rename), читает синхронно на старте (файл десятки
килобайт), пишет асинхронно на `Dispatchers.IO`, и `flush()` при `onPause()`. Если объём истории вырастет
до тысяч материалов — замена на Room точечная: репозиторий уже единственный, кто знает про хранилище.

## LLM-слой

```kotlin
interface LlmClient { suspend fun complete(brief: LlmBrief): LlmResult }
```

* `OpenAiCompatLlm` — один `POST {baseUrl}/chat/completions`, OkHttp, `suspendCancellableCoroutine`,
  таймауты, разбор `choices[0].message.content` (+ `reasoning_content` для моделей-рассуждателей).
  Никакого собственного бэкенда: запрос идёт из приложения напрямую провайдеру.
* `OfflineLlm` — шаблонный движок на 24 действия; используется как fallback при ошибке/отключении модели.
* `ShiftEngine.runTask` пробует удалённую модель, при падении дописывает событие `WARNING` и доводит
  задачу офлайн-движком. Отказ не роняет смену и не оставляет «вечную» задачу: `FAILED` — тоже терминальный статус.

Промпт собирается в одном месте — `GrowthAgent.systemPrompt/userPrompt`: персона агента + контекст канала
+ инструкция действия + блок ограничений (`SafetyPolicy`). Требование «без накрутки» живёт не только
в промпте: у агента просто нет транспортного слоя для записи на площадку.

## Точки расширения

| Что добавить | Где |
|---|---|
| новое действие агента | один кейс в `TaskKind` + шаблон в `Templates.render` + строка в `Playbooks` |
| нового агента | `AgentId` + класс `: GrowthAgent` + `AgentRegistry.all` + `Playbooks.forAgent` |
| свой провайдер модели | реализовать `LlmClient` (например, локальная модель через MediaPipe/llama.cpp) |
| запись метрик из Studio API | `YouTubeDataApi` + новый `MetricsSource`, репозиторий менять не нужно |
| экспорт отчёта в PDF/Telegram | поверх `ShiftReport`, данные уже сериализуемые |
